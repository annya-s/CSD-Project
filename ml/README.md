# Offline winter-wheat biomass experiment

This directory is a self-contained Python experiment using a fixed local research dataset. Preprocessing, training, evaluation, scenario generation and prediction run without contacting a dataset or weather service. There are no dataset-download scripts. Dependency installation is a separate setup step that may require package access.

The numerical target is **measured dry aboveground winter-wheat biomass in g/m²**, from `AGBd_wheat` on its recorded `AGB_N_date`. It is not a crop-health percentage, disease diagnosis, yield forecast or proven irrigation recommendation. The current model is **EXPERIMENTAL** and is not validated for Singapore, other crops or hydroponics.

## Conditions and inputs

The model uses four weather conditions plus planting age:

| Input | Representation | Unit |
|---|---|---|
| Air temperature | Mean over previous 7 and 14 complete local days | °C |
| Vapour pressure deficit (VPD) | Mean over previous 7 and 14 complete local days | kPa |
| Soil moisture at **0–7 cm** | Mean over previous 7 and 14 complete local days | m³/m³ volumetric fraction |
| Sunshine duration | Mean daily sunshine over previous 7 and 14 complete local days | hours/day |
| Planting age | Prediction date minus sowing date | days |

That is **nine numerical features**. Relative humidity and daylight duration are required auxiliary history fields for consistency checks and scenario generation; they are not additional direct model features. Latitude/longitude, crop and growing system are required for support checks, not numerical training predictors. Soil moisture at 3–9 cm cannot simply be renamed 0–7 cm.

`examples/request.json` is a complete accepted request. It includes `crop: winter_wheat`, `growing_system: outdoor_soil`, sowing/prediction dates, field coordinates and a `weather-history-v1` history with the `ifs-soil-0-7-v1` profile. History must contain exactly the preceding 14 complete local days (excluding prediction day), an IANA timezone, hourly Unix timestamps, matching units, and daily sunshine/daylight totals. DST days are handled by timestamps, rather than assuming every fortnight has 336 hours. No missing-value imputation is performed.

Support is restricted to training geography and each feature's training range, recorded in `artifacts/wheat_biomass_v1/feature_schema.json`. Training planting ages span 148–263 days. Requests outside supported context return a structured state with no numerical prediction.

## Layout and preprocessing decision

`data_preprocessing.py` is the single offline entry point. It calls small modules in order: `prepare` → `features` → `splits` → `synthetic`. Keep those modules separate for parsing, feature validation, split integrity and scenario tests. `predict.py` remains separate because live inference should load a saved model, not rerun dataset preparation or create synthetic rows. `weather.py` contains offline normalization utilities for already-saved provider responses only; the normal pipeline consumes the included normalized snapshot.

- `data/raw/zenodo_17475742/`: four unchanged local source TXT files, including the two explanatory files. Original copies directly under `data/raw/` are preserved when present. Header whitespace is normalized in memory, never by rewriting source files.
- `data/manifests/`: source provenance and checksums. Local import does not need Internet metadata. Original downloaded provenance is retained alongside the locally generated hash manifest.
- `data/processed/weather_windows.json`: included, static normalized weather input with original request, retrieval and provider-grid metadata. Optional raw HTTP response cache is retained locally but is not needed by the pipeline.
- `data/processed/`: observed rows, nine-feature table and explicit rejection/audit files; these small outputs are also reviewable in version control.
- `data/splits/wheat_v1.json`: frozen field-season assignments. A mismatched dataset fails instead of silently replacing the split.
- `data/synthetic/`: reproducible engineering scenarios; generated files are ignored by version control.
- `artifacts/wheat_biomass_v1/`: locally generated models, feature schema, selection and model card; ignored and regenerated by training.
- `reports/wheat_v1/`: actual candidate metrics, prediction rows and the readable experiment report.
- `examples/`: real offline request/response demonstration and its provenance, using a training window. This is not independent evaluation evidence.

All changes and outputs remain under `ml/`. Existing Java/frontend code and database tables are not modified.

## Run locally (PowerShell from repository root)

The existing `ml/.venv` is installed and ready; skip setup on this machine. For a fresh checkout, install/register Python 3.12 first (the `py -3.12` command requires it), create the environment only if absent, then install the locked dependencies and package:

```powershell
py -3.12 -m venv ml/.venv
ml/.venv/Scripts/python.exe -m pip install -r ml/requirements-lock.txt
ml/.venv/Scripts/python.exe -m pip install --no-deps --no-build-isolation -e ml
```

With dependencies installed, every command below uses local files only:

```powershell
ml/.venv/Scripts/python.exe -m csd_weather.data_preprocessing
ml/.venv/Scripts/python.exe -m csd_weather.train
ml/.venv/Scripts/python.exe -m csd_weather.evaluate
ml/.venv/Scripts/python.exe ml/scripts/create_example.py
ml/.venv/Scripts/python.exe -m csd_weather.predict --request ml/examples/request.json --output-dir ml/predictions
ml/.venv/Scripts/python.exe -m pytest ml/tests --basetemp=ml/.test-tmp/pytest -q
```

Use `--skip-synthetic` on preprocessing to rebuild only observed data/features and splits. Missing static inputs fail clearly; no command falls back to a download. Training reads only `OBSERVED` rows and rejects synthetic or mixed-profile data. It fits a median baseline, polynomial age-only baseline and fixed-configuration CatBoost model. It saves all candidates, the validation-selected artifact, its checksum and supporting metadata. Evaluation recomputes metrics from the saved observed prediction table; it does not retrain.

The fixed scenario configuration produces **1,000** rows: 700 resampled training histories, 200 perturbed histories and 100 deliberately invalid cases. The 900 valid cases test pipeline robustness; the 100 invalid cases must be rejected. All biomass labels are null. Scenarios are never fitted or scored as real biological observations. They retain training-parent IDs, family, seed, source references and allowed use. Temperature perturbations recompute VPD at the same relative humidity; sunshine perturbations update hourly and daily values together. These are engineering fixtures, not a calibrated plant-growth simulator.

## Actual evaluation

The static sources contain 198 valid dated biomass observations. Of these, 178 have usable weather windows; 20 November 2016 observations precede the selected weather profile coverage. The model uses 88 training rows, 32 grouped validation rows and 58 rows in the later season temporal holdout. The source has few independent fields, grids and dates; row count is not sample independence.

| Candidate | Validation MAE (g/m²) | Temporal holdout MAE (g/m²) |
|---|---:|---:|
| Median | 495.28 | 318.03 |
| Age only | 183.97 | **58.04** |
| CatBoost | **74.18** | 123.61 |

CatBoost was selected using validation only. **Weather did not improve the temporal holdout over age alone.** The selected artifact stays experimental; the test result was not used to retune or change the frozen selection. Even within the training age range, holdout MAE is 87.45 for CatBoost versus 81.31 for age-only (30 rows). The other 28 holdout rows remain in the primary metrics.

There are **6 provider grid cells and 38 distinct grid/date groups**. Train/validation/test contain 25/8/9 grid/date groups, including 4 shared by train and validation. Location-specific request-window IDs are not independent weather samples. This overlap weakens validation evidence. The temporal holdout covers November and April only, and there is no cross-region validation. Read `reports/wheat_v1/report.md` and `evaluation.json` for all errors, subgroup analyses, hashes and limitations.

## Local prediction and private API

The included demonstration returns about **152.02 g/m²**, status `EXPERIMENTAL`, with null confidence and interval. Responses contain the input hash, model version/hash, support reasons and extracted features. Rules-based weather advice is explicitly separate from the regression and does not establish a biological diagnosis. Identical inputs/model versions have a stable prediction ID. The CLI and API save JSON under `ml/predictions/`; neither reads nor writes a database.

Supported response states are `EXPERIMENTAL`, `UNSUPPORTED`, `INVALID_INPUT` and `UNAVAILABLE`. Malformed top-level requests and invalid nested history both return HTTP 422 with `INVALID_INPUT` and the message: "Check the input and provide 14 complete days of weather history." Missing, inconsistent or corrupt model artifacts make readiness fail.

```powershell
$env:ML_API_TOKEN = 'replace-with-a-private-server-token'
ml/.venv/Scripts/python.exe -m csd_weather.service --host 127.0.0.1 --port 8001
```

From another terminal, use the same server token:

```powershell
$headers = @{ Authorization = "Bearer $env:ML_API_TOKEN" }
Invoke-RestMethod http://127.0.0.1:8001/ready -Headers $headers
Invoke-RestMethod http://127.0.0.1:8001/predict -Method Post -Headers $headers -ContentType 'application/json' -InFile ml/examples/request.json
```

Without a token, only loopback callers are accepted. Binding outside loopback requires a token. This is a private backend API, not a browser endpoint. Disable untrusted proxy forwarding and supply trusted backend ownership if exporting. `.env.example` documents optional environment variables; it is not automatically loaded. Load only locally produced trusted artifacts, especially joblib files.

## Future database connection

For the school application, start with the [Java integration guide](INTEGRATION.md): run Python as a separate local process, let Java read compatible stored history, and have Java POST the request to `http://127.0.0.1:8001/predict`. **This connection is not implemented yet.** Python does not fetch weather. The existing database needs additional history before real application records can be used.

The direct database → Python → database job described below is an alternative prepared adapter, not a prerequisite for the Java HTTP approach. Live reads and writes remain disabled by default; neither workflow makes today's stored snapshot sufficient.

**The current database cannot directly supply this contract.** The existing weather repository stores a latest snapshot, omits VPD even though the client fetches it, and uses forecast soil moisture at 3–9 cm. This model needs 14 complete historical days and 0–7 cm soil moisture under a compatible weather profile. The prepared adapter preserves timestamps, units, profile, depth, timezone and planting context, and returns insufficient history while coverage is missing. Renaming fields or fabricating historical rows is not valid. A different profile/depth requires a separate model and validation. Database integration and backend changes are pending, outside this directory's implementation.

Optional future Supabase export is prepared but **disabled and unapplied**. `sql/001_ml_predictions.sql` is a reviewable SQL draft restricted to the service role; it has not been run. `persistence.py` requires trusted application `farmer_id` and owned planting timestamp, `SUPABASE_ENABLED=true`, an HTTPS project URL, a server-only secret, and an explicit `--upload`. The numerical API never invokes it. Do not expose service credentials or accept browser-supplied ownership.

After separately setting up the intended database and adding validated ownership to a saved prediction, preview its export without network access:

```powershell
ml/.venv/Scripts/python.exe -m csd_weather.persistence --prediction ml/predictions/OWNED_PREDICTION.json
```

Only adding `--upload` with the required environment settings performs an insert. No database credentials are configured or required for the offline workflow.

## Verification

Run tests from the repository root using the ML environment. `pytest` discovers functions named `test_...`; a file path narrows the files and `-k` filters test names. These commands check existing code and use local fixtures/fake database transports:

```powershell
# Everything
ml/.venv/Scripts/python.exe -m pytest ml/tests --basetemp=ml/.test-tmp/pytest -q
# Only the stored-history adapter tests
ml/.venv/Scripts/python.exe -m pytest ml/tests/test_database.py --basetemp=ml/.test-tmp/pytest -q
# One concrete test: database fixture and saved request produce the same features/prediction
ml/.venv/Scripts/python.exe -m pytest ml/tests/test_database.py -k test_fixture_matches_golden_features_and_prediction --basetemp=ml/.test-tmp/pytest -q
```

The suite covers feature boundaries/DST, physical units, frozen splits, synthetic-label exclusion, artifact consistency, authenticated API requests, malformed histories, stored-row conversion, database query bounds/truncation, fixture upload protection and disabled export. A dependency may warn about Starlette's HTTPX test client. Restricted Windows environments can block the local socket pair used by API tests; that is an execution-environment issue, not evidence that the application is connected.

A separate clean-copy check rebuilt all 198 observations, 178 feature rows and 1,000 scenarios using only the included canonical TXT files, normalized weather snapshot, split manifest and configuration, with network calls blocked and no raw HTTP cache. Saved candidate errors were recomputed and matched the report; the final feature-table hash matches the trained model report. The example request was run through the actual saved artifact and CLI.


## Database rows → Python prediction (prepared, disconnected)

`database.py` reads the proposed `ml_planting_context`, `ml_weather_hourly` and `ml_weather_daily` contract. `sql/002_ml_weather_history.sql` is a **new, unapplied draft**, not a mapping of the current latest-snapshot tables. A future collector/backend change must provide compatible IFS history, VPD, RH, 0–7 cm volumetric soil moisture, hourly sunshine seconds and daily astronomical daylight. Ownership must be verified by the trusted backend against the application's planting records. The context keeps the planting timestamp and actual agronomic sowing date separate. Service-role-only grants and RLS prevent browser access; service credentials themselves bypass RLS.

Run the direct Python workflow from the repository root, without credentials or any network call:

```powershell
ml/.venv/Scripts/python.exe -m csd_weather.database_predict --fixture ml/examples/database_fixture.json --output-dir ml/predictions
```

Omitting `--fixture` selects that same fixture. It is derived from the existing archived `request.json` weather, with fictional owner **1001**, no real user association. It reproduces the same features and approximately **152.0214 g/m²** prediction. `--upload` is prohibited for fixture input. The CLI saves results locally; malformed/incomplete history produces a structured status instead of an HTTP 500. No new training, dataset acquisition or weather-provider fetch is involved.

After separately reviewing/applying both SQL drafts, populating history, configuring server-only credentials, and validating ownership, the future read-only command is:

```powershell
$env:SUPABASE_READ_ENABLED = 'true'
# Set SUPABASE_URL and SUPABASE_SECRET_KEY in the trusted server environment.
ml/.venv/Scripts/python.exe -m csd_weather.database_predict --from-database --farmer-id TRUSTED_FARMER_ID --planted-at 'OWNED_ISO_TIMESTAMP_WITH_OFFSET' --prediction-date 'YYYY-MM-DD' --output-dir ml/predictions
```

Replace the uppercase placeholders with backend-authorized values. The example is a template, not an instruction to connect now. Reads request the exact previous 14 local calendar days with DST-aware UTC bounds, require 14 daily rows and every hourly instant, and reject duplicates, wrong ownership/profile/depth, future windows and truncated responses. Data API requests use fixed columns, bounded timeouts, disabled redirects and exact response counts. No missing RH, VPD or historical rows are fabricated. Operational failures (unavailable input/model or upload failure) exit with code 1 after saving/reporting the local result; supported validation statuses remain structured results.

To complete a future database → Python → database job, separately set `SUPABASE_ENABLED=true` and append `--upload` to that live command. Read permission alone never enables writes. Modern `sb_secret_...` keys use only the `apikey` header; legacy service-role JWTs also use Bearer authorization. Neither keys nor response bodies are printed. These are private server operations, not a public/browser CLI deployment. See the official [Supabase Data API documentation](https://supabase.com/docs/guides/api) and [API-key guidance](https://supabase.com/docs/guides/getting-started/api-keys).
